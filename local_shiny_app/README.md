# RentLens (`rentalapp`)

Live: https://01a18a24-12d4-aa74-2e7f-2340d690bbe1.share.connect.posit.cloud/

A Shiny app for renters: a first-visit setup wizard and personal filters ("My
filters"), budget check, listing check, options within budget, map
(with key places, MRT/LRT stations and map selections applied to every page),
area comparison (districts, Area A vs B), property comparison, value for
money, shortlist and raw transactions. It is structured as
an R package, following
[Engineering Production-Grade Shiny Apps](https://engineering-shiny.org/structuring-project.html).

## Run it

```r
# one-time
install.packages(c("shiny", "bslib", "DT", "dplyr", "plotly", "sass",
                   "leaflet", "leaflet.extras", "sf", "httr2", "pkgload", "testthat", "roxygen2"))

shiny::runApp("local_shiny_app")      # from the repo root, or "Run App" on app.R
```

### How the pieces talk to each other

- `mod_settings_server()` owns the renter's settings (budget, places that
  matter, where to search, type of home, commute and MRT). `mod_filters_server()`
  turns them, plus the Search page's quick District and Project filters, into
  reactives (`market`, `selection`, `comparables`, `budget`, `places`, ...).
  Every other module receives that list as `filters`.
- The shortlist is a `reactiveVal` created in `app_server()` and passed to the
  modules that add to it (Within budget, Map) and show it (Shortlist,
  Compare properties).
- The map selection (`new_map_selection()`) and saved areas
  (`new_saved_areas()`) are `reactiveValues` created in `app_server()`. The
  map writes them; `mod_filters_server()` applies the selection to `market`
  (the map itself uses `base`, before the selection), and Area A vs B reads
  the saved areas.
- Rental data is read once per R session by `rentals_data()` (`fct_data.R`),
  which also attaches each contract's nearest MRT/LRT station.

### My filters and the setup wizard

The code calls them settings (`mod_settings.R`, `fct_settings.R`); the app
calls them "My filters".


- Settings are saved in the **browser** (`localStorage`, key `rentlens-settings`),
  not on the server: there are no accounts, and each browser has its own
  settings. `inst/app/www/settings.js` reads them when the app connects and
  sends them to the server as `input$"settings-stored"` (`"none"` if nothing is
  saved); the server saves them back with the `rentlens-save-settings` message.
- Nothing saved = first visit: `mod_settings_server()` opens the setup wizard
  (budget, places, where to search, type of home, commute and MRT, with a
  preview of the closest homes). Finishing saves the settings, opens the Search
  page and shows a tip on the options list and "Add to shortlist".
- "My filters" (navbar) or "Edit my filters" (the My filters box at the top
  of every page) opens the same sections as tabs. "Start over" clears the saved settings and reruns the
  wizard. To see the wizard again while developing, run
  `localStorage.removeItem("rentlens-settings")` in the browser console.
- `fct_settings.R` defines the settings: `default_settings()`,
  `settings_to_json()` / `settings_from_json()` (which checks each field and
  falls back to its default, so stale saved settings can't break the app) and
  `settings_summary()`.
- "Save search" links carry the settings; opening one applies them for that
  visit without replacing what the browser saved.

### Naming conventions

| Prefix   | Contains                                | Example                    |
|----------|-----------------------------------------|----------------------------|
| `mod_`   | a Shiny module: `mod_x_ui()` + `mod_x_server()` | `mod_map.R`       |
| `fct_`   | app logic with no Shiny inputs/outputs  | `budget_verdict()`         |
| `utils_` | generic helpers                         | `money()`                  |

## Deploying (Posit Connect Cloud)

The app is live at https://01a18a24-12d4-aa74-2e7f-2340d690bbe1.share.connect.posit.cloud/, published on
[Posit Connect Cloud](https://connect.posit.cloud) from GitHub: every push to
`main` redeploys it automatically.

- Connect Cloud installs the packages listed in `manifest.json` (next to
  `app.R`). After adding or updating a package, regenerate it and commit it:
  `rsconnect::writeManifest(appPrimaryDoc = "app.R")` (also run by
  `dev/check.R`).
- One-time setup: on connect.posit.cloud, sign in with GitHub, **Publish** →
  **Shiny**, repo `juniper285/dba3702-group1`, branch `main`, primary file
  `local_shiny_app/app.R`, "Automatically publish on push" on. The free plan
  needs the repo to be public.
- Nothing is written on the server: settings live in each visitor's browser,
  and OneMap/data.gov.sg need no keys.

## Development workflow

```r
# from local_shiny_app/
source("dev/run_dev.R")        # reload code and launch
source("dev/check.R")          # regenerate NAMESPACE + run tests
```

- Added a new `@importFrom` / `@export` tag? Run `roxygen2::roxygenise()`.
- Adding a tab: create `R/mod_newtab.R` with `mod_newtab_ui(id)` /
  `mod_newtab_server(id, filters)`, then add one line to `app_ui.R` and one to
  `app_server.R`.
- Data changed? Put the new `URA_Union_Cleaned_with_Address.xlsx` in `data-raw/`,
  then `source("data-raw/rentals.R")`.
- "Check a listing" looks up addresses with the OneMap Search API (no key
  needed); answers are cached for the R session.
- Key places (universities, polytechnics, business districts, transport,
  hospitals) are listed in `destination_groups` in `R/fct_location.R`.
